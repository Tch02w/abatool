# 本机队列调度与恢复（F004/F005）

WinUI 的正式队列由 Qt-free Python 控制面调度。`LocalQueueScheduling` 复用原提交器的 `SchedulerCore`、队列投影和 SQLite 存储；页面只提交参数、显示状态。PySide6 对照入口保留。此处是本机资源准入，不代表跨节点 Slurm 调度。

## 重启动依赖的失败与恢复

前置作业运行期间，子作业显示“等待前置”。前置成功且其 ODB 已就绪后，子作业进入资源分配。前置失败时，子作业显示“运行失败”，备注指出前置作业名称，执行编号和等待原因均为空。其他满足 CPU、内存与并发条件的作业继续调度。

后台恢复历史队列时，会清除已结束行遗留的等待原因。已有调度事件原样保留。同一失败状态在后续调度检查和再次打开队列时只记录实际发生的那次变化。实现和核验位置见 [TASK-002 混合队列验收](../08-handoff/ACTIVE_TASKS/TASK-002-migration.md#混合队列的资源准入与失败依赖)。

## 队列来源一致性

一个后台实例的队列页、资源统计、重启动链、完整结果预览和批量执行前复核均使用该实例的 `JobQueueService.path`。显式配置独立 `joblist_path` 时，不再读取进程默认队列；未指定时仍沿用原应用数据路径。HTTP 请求/响应字段不变，也不增加文件迁移。找不到目标或计划发生变化时保留原错误，不回退到另一队列，不启动合并。此修正不改变取消、归档或求解行为。自动检查用两份不同队列验证来源和另一文件不变；工程及原生验证范围见[交付核对](../06-testing/COMPLETION_AUDIT.md)。

## 已有调度库、首次建库和后台启动失败

调度库保存作业快照和事件。打开已有的版本 1 数据库时，后台先核对表、字段、索引和版本。已启用 WAL 且结构完整的旧库，可在另一连接持有写事务时读取上次已提交的记录。旧库的表名或字段名大小写不同、用户触发器与表同名，均可保留原有作业和事件。

遇到独占锁会报告数据库忙，释放占用后可用同一文件重试。遇到更高的版本会提示当前支持的版本，原库内容保留。已确认 SQLite 文件损坏或已知调度表结构不兼容时，才沿用原有的备份重建流程，备份名带有 `.corrupt-` 和时间戳。缺少的表或索引可在一次写事务内补建。

合并、批量完整结果、远端作业、作业通知和后处理分组队列使用独立的操作历史库。首次建立其中一个库时，后台取得该库的所有权锁，在同目录临时文件中完成建表并写入版本，关闭连接后才发布到正式路径。建库过程中抛错会清除临时文件，下一次启动可以重新建库。如果正式路径上原已有无效文件，后台报告错误并保留原件。

空库首次建表使用 `journal_mode=MEMORY`，把这次事务的回滚日志放在内存中，临时数据库文件按 `synchronous=FULL` 提交。SQLite 指出，进程在这种事务中崩溃可能损坏数据库。因此该设置只用于尚未发布且可重新创建的空库。正式文件发布后，后台另开连接，使用磁盘回滚日志和 `synchronous=FULL` 保存业务记录。[SQLite 日志模式说明](https://www.sqlite.org/pragma.html#pragma_journal_mode) · [冷启动与中断验收](../08-handoff/ACTIVE_TASKS/TASK-002-migration.md#2026-11-28--空操作历史库的首次启动)

后台启动中途失败时，按创建顺序反向关闭本次已经打开的服务、数据库和监听端口。已验证本机调度器初始化失败和发布连接信息失败两种情形。两种情况下旧连接信息都保留，重新启动后作业通知接口恢复可用。代码入口为 `SQLiteSchedulerRepository._initialize`、`OperationJournal._create_database` 和 `ControlPlaneRuntime.__init__`。[测试条件与回执](../06-testing/COMPLETION_AUDIT.md#历史库与后台启动失败)

## 候选与正式作业的目录设置（F004）

在「作业队列」勾选候选作业，点击「批量设置目录…」。单条候选和可编辑的正式作业也能分别调整。批量编辑可以只改计算根目录、归档根目录或归档后的清理选择。填写文件夹时使用已存在的绝对路径。保留字段时沿用各条记录自己的值，显式清空计算根目录后回到 INP 工作目录，清空归档根目录后停用归档。

计算根目录是存放各作业的父目录。设置为 `G:\SSD` 后，作业 `CaseA` 的计算目录为 `G:\SSD\CaseA`。归档根目录是保存结果的父目录。实际发布的位置另行记录，遇到重名可能带后缀。调整下一次作业设置会保留上一次归档的实际发布路径。

修改队列项时，填写两个目录不会自动开启清理。已有清理选择在两个目录仍有效时保留，清空任一目录会关闭清理。明确开启清理需配置计算和归档根目录，归档标记须已启用，原始 INP 在拟清理目录以外，执行阶段仍需完成归档校验。归档根目录不能设在作业实际计算目录内。旧的「新建作业」草稿及 PySide6 建立候选时，按原有约定，两目录都填时可默认启用清理。可在队列编辑中核对并关闭。

修改按明确选中的作业标识一次保存。标识失效、目录不可用，或设置后与其他候选或尚未终结的正式作业同目录同名时，整批保留原配置。未填 Restart 前置 ODB 等问题仍可在下一步修正，正式入队会再次校验。运行中和归档中的正式作业沿用其编辑保护。

队列文件保留历史的 `archive_after_complete` 标记与 `archive_dir` 路径。旧记录若同时出现非空归档路径及关闭的标记，当前 WinUI 本机执行器按路径归档。仅编辑优先级、CPU 等字段时后台保留原标记和清理选择。要停止这类记录的归档，可清空归档根目录。设置新归档路径会同步刷新标记。接口字段与错误见[控制面约定](../api-contract.md)。

## 正式队列的重启动依赖编辑（F011）

在「重启动链 → 编辑依赖」选择或输入前置 ODB。该页面只向后台提交选中作业的标识和前置路径。前置作业已在队列中时可填写预期输出路径，外部前置作业须有实际 ODB。多个队列作业同名时按 ODB 所在目录区分。清空含 Restart 指令的作业依赖后，作业进入「等待前置」。

「校验全部」会沿每个重启动作业的父链检查。直接发生循环、缺少前置或 ODB 路径冲突的作业显示具体原因。依赖该作业的后续节点显示「上游依赖异常」，详情给出最近出错的前置作业名和原因。「生成此节点完整结果」在这些节点上禁用，依赖正常的其他分支仍可预览计划。依赖校验中的有效计数只计入整条父链通过的重启动作业。环及通往环的作业显示「阶段未定」。预览计划时会另行检查各阶段 ODB 是否已生成。

`GET /api/v1/restart-chains` 在 `nodes` 与 `graphNodes` 中使用相同的 `validationStatus`、`validationMessage`。间接受影响的节点返回 `upstream_invalid`，数量计入 `checks.upstreamInvalidCount`。循环、缺失前置和路径冲突的计数仍按直接错误统计。三级 GJB-16 工程及同名根路径负例见[验收记录](../08-handoff/ACTIVE_TASKS/TASK-002-migration.md#三级-gjb-16-工程与上游依赖校验)。

后台在保存前校验自引用、间接循环、丢失的前置作业和路径冲突。拒绝后原链、作业状态及其他参数保持原值，界面显示「重启动依赖未保存」。候选确认按实际入队的整批作业校验，草稿入队和正式队列编辑也会检查相应依赖。调度期间修改依赖须先停止调度。普通求解失败仍按队列既有的重新排队流程处理。

重新排队也会复核重启动依赖。旧文件中已处于待运行状态的错误依赖会在派发前进入「等待前置」，即使自己目录下已有同名 ODB，也会提示修正循环。

旧版曾把依赖输入错误记为「运行失败」。其中保留了旧校验提示和无效标记、仍存在相应命名问题、且无执行尝试、进程、外部接管或归档等证据的记录，可以直接改正前置 ODB。已重启的控制面也能识别这种记录。纠正时只允许更改依赖，作业的优先级、资源和暂停调度设置保留。取消编辑不会提交修改。

## 输入与派发顺序

- 输入为正式队列条目及「并行上限」。待运行且未暂停调度的条目必须设置 Core；0 表示未设置，开始请求返回字段错误。
- 先检查 Restart 前置作业，再按优先级从高到低、相同优先级的队列顺序分配。移动上下顺序只影响相同优先级的条目。
- 同名 Restart 父作业按明确的 oldjob 路径区分，包含计算根目录生成的实际工作目录。有多个未消歧的同名父作业时等待用户指定路径。队列父作业仍运行时，即使旧 ODB 已存在也不放行；没有队列父作业的外部 ODB 仍检查文件和 LCK。
- 同目录同名作业互斥。正在结束的执行线程和归档占用不会提前释放。

## 资源口径

派发到本机执行器后，先只读验证工作目录和命令，再逐文件准备输入。已有 LCK、缺失前置文件或取消策略拒绝时不会先覆盖目标输入；失败持久恢复后不自动重试。复制、取消和归档限制见 [工作目录准备](LOCAL_WORKSPACE.md)。

| 项目 | 本机准入规则 |
|---|---|
| 作业槽位 | 并行上限减去已观察到的活动作业及尚未收尾的本机执行记录 |
| 单作业 CPU | 沿用软件版本规则：Abaqus ≤2021 按逻辑线程，>2021 按物理核心；不是许可证规则 |
| 合计 CPU | 使用本机逻辑线程总数减活动队列作业的 Core，再逐项扣除新分配；活动外部作业的 Core 未知时不当作 0，暂停新的 CPU 分配 |
| 绝对内存与估计 | 取绝对配置与有来源估计的较大值；从系统可用内存的 85% 中扣除活动作业需求尚未体现在新鲜 RSS 中的部分，避免重复扣已驻留内存 |
| 百分比内存 | `90%` 是传给求解器的上限，不能当作实际占用或固定预留；当前不据此推算需求 |

已接入旧纯 Python 内存学习器、自有进程采样和后台重启后的历史估计，按模型身份区分，并显示估计来源。百分比设置仍不能保证总内存充足。冷启动、文件元信息、采样失败和峰值余量限制见 [内存观测说明](MEMORY_MONITORING.md)。实际 Windows helper 及自动测试不等于真实 Abaqus/MPI 高负载和原生业务验收。

## 持久状态、错误和取消

队列同目录中的 `scheduler_state.db` 保存作业、事件和每次执行的 `attemptId`；`joblist.json` 保留界面队列。分配必须完成两个存储的写入才可启动线程。两个文件不是一个跨文件原子事务：中途崩溃后保守恢复为「状态未知」，不根据保存的启动状态重复执行。

后台重启后不自动恢复派发。JSON 或 SQLite 中尚活动的记录，以及此前未核对的记录，保留执行身份并登记原工作目录扫描。SQLite 中有活动条目但 JSON 缺行时，重建仅供观察的外部条目。扫描更新的是实际状态，不重新取得进程控制权。观察到的外部作业不自动获得暂停/终止能力。

「状态未知」会阻止新资源分配，也不能被清理完成记录、删除或重新排队。扫描后若没有活动/结束证据则显示「待确认」，用户核对后才能明确重新排队。它不表示成功或零结果。原执行器返回未知时同样保留并扫描，退出检查不会把它当作安全空闲。

存储或线程启动失败会暂停新派发并在队列显示原因。启动失败释放未启动分配；运行中进度保存失败继续监控原执行器；最终结果保存失败保留未收尾状态，每 5 秒重试保存，绝不重新运行计算。保存成功后由用户重新开始队列。停止队列只停止派发；终止请求继续沿用自有执行器的合作停止。后台继续和关闭协议见 [退出说明](UI_INTERACTION.md)。

## 外部作业扫描与并发修改

在正式队列的「工作目录 → 扫描」读取外部作业。扫描期间 API 的 `externalScanActive` 为 true，页面显示「扫描中…」并禁止重复启动；状态读取返回最近已保存的队列，不等待进程枚举、目录检查或日志诊断。同一后台只进行一轮外部扫描，多目录共用一次进程列表。重复手动请求返回 409 `EXTERNAL_SCAN_BUSY`，周期扫描遇忙跳过本轮。

扫描在独立副本上计算结果，结束后重新读取当前队列。只有完整原记录仍匹配的条目才允许更新；扫描期间被编辑、删除、重新执行或被同名同目录条目替换的结果会跳过，且保留候选区和当前排序。本机执行器管理的活动记录及正在归档的记录不接受扫描覆盖。统计中的新增、更新按实际落盘计数；`staleResultsSkipped` 表示跳过的旧结果，可稍后刷新核对。

扫描失败不保存部分结果并释放扫描占用；关闭后台后不再合并迟到结果，手动请求返回 503 `CONTROL_PLANE_SHUTTING_DOWN`。扫描本身没有独立取消按钮；此修改也不意味着线程中的系统调用可即时终止。识别外部进程仍沿用目录、作业名、状态证据规则，不获得求解控制权；没有结束证据不能报告成功。

源码定位：`JobQueueService._run_external_scan`、`_scan_external_roots` 和 `external_job_scan_core.scan_external_jobs(additional_roots=...)`。回归入口 `tests/control_plane/test_external_scan_concurrency.py`；真实 Windows 自有非求解进程与生产 C# 客户端验证为 `packaging/verify_external_scan.py`。小型夹具响应时间不能代表工程负载或网络目录性能，原生界面显示仍需验收。锁与合并约定见 [ADR 0015](../submitter/adr/0015-external-scan-snapshot-merge.md)。

## 输出与性能边界

相同路径的历史内存查询在单轮共享文件元信息，空历史不扫描文件；无活动归档时省去归档目录比较。缓存不跨轮，作业配置与准入规则不变，详见 [内存说明](MEMORY_MONITORING.md)。正式客户端/实际进程场景入口为 `packaging/verify_scheduler_load.py`，包含261条队列记录与5次受控执行，覆盖优先级/CPU、超大声明内存等待后编辑放行、停止派发不杀现有作业、单项终止、失败后资源释放和重启不重放；不代表工程高负载验收。

队列显示槽位、CPU、内存、依赖或目录冲突的等待原因；运行 API 增加 `schedulerMessage` 和操作的 `attemptId`。相同队列内容不重复替换 JSON，相同状态及消息不重复写调度事件。过期执行回调不能覆盖已完成结果。

源码：`modules/control_plane/local_scheduling.py`、`local_queue_runtime.py`、`job_queue_commands.py`，共享算法位于 `modules/submitter/scheduling.py`、`scheduler_adapter.py`、`scheduler_repository.py`。验证入口为 `tests/control_plane/test_local_scheduling.py`、`test_local_queue_runtime_api.py`、`test_shutdown_guard.py` 和 `tests/submitter/test_scheduler_adapter.py`。本轮实际结果与未验收范围见 [TASK-002](../08-handoff/ACTIVE_TASKS/TASK-002-migration.md)。
