# ADR 0006：合并操作的持久记录与保守恢复

状态：已实现，实际后台异常退出与 HTTP 重建由自动化验收；原生页面交互仍待验收。

## 问题

F013 的异步合并状态原先仅存在于控制面内存，后台重启后无法恢复请求身份、结果与失败记录。原生页只选择最近成功记录，可能隐藏较新的中断。此前调用者的重复请求标识也会在重启后失效。

合并执行器只在隔离副本中调用外部 Abaqus，最终结果由控制面在校验后发布。控制面突然退出时，外部进程和目标发布状态都可能未确认；看到输出文件本身不能证明该次操作已完成。

## 决策

1. 在 descriptor 同目录保存 `odb-merge-history.sqlite3`。独立文件锁保证仅一个控制面拥有记录写入权，SQLite 事务和 FULL 同步保护每次已确认检查点。损坏、未知版本或被占用均保留原文件并拒绝新合并。
2. 启动执行前持久化请求身份、规范化路径、配置、操作与尝试标识。状态边界和最终结果立即写入；高频进度/日志每 0.5 秒最多持久化一次，尾部保留 200 行。每次仅更新单条记录，避免日志更新重写全部历史。
3. 重启时恢复终态记录与请求身份。同一请求标识重试返回既有操作；参数改变仍冲突。原始请求签名独立保存，不能用自动编号后的目标路径代替。
4. 非终态记录转为 `failed` / `ODB_MERGE_INTERRUPTED`，界面显示“合并中断，待核对”。保留来源、目标、最后检查点和日志，明确外部进程状态未知；不自动重跑、不自动清理旧工作区，也不据文件存在改标成功。已提交结果但最终状态落盘前退出，同样需要核对。
5. 运行中记录写入失败时停止接受新任务并请求取消未发布操作；已经提交的结果保留成功事实及保存失败提示。磁盘记录可能落后于内存，此时退出检查不能同意终止后台。
6. 现有 `/api/v1/odb-upgrade-shutdown-check` 在保留响应结构的同时，原子检查并预留升级和合并两类管理器。固定锁顺序；任一不安全时，另一类也不进入停止预留状态。
7. 合并页恢复最新操作，显示失败和中断，并保留部分结果提醒、回执路径及持久化告警。加载新的结果图计划时不被历史草稿覆盖。

## 影响与边界

使用 Python 标准库 SQLite，无新增运行依赖。数据库和锁属于用户运行数据，不随源码或发布目录分发。旧版本的内存历史无法追溯恢复。SQL 行记录保存的是历史操作事实；文件后来被移动或修改时，不能把历史成功当作当前文件再次验证。

本决策覆盖 F013 单步操作，包含 F012 内部调用的单步记录。后续[ADR 0007](0007-durable-result-batches.md)已将F012批量计划和游标移至后台持久保存，恢复须显式检查并继续；已提交子任务中断时不重放。其他后处理/远端操作的持久恢复需各自核对；不能由本 ADR 推断全部异步任务恢复完成。

测试入口：`tests/control_plane/test_odb_merge_recovery.py` 包含独立测试进程真实强制退出（不启动 Abaqus）、HTTP 控制面重建、请求去重、损坏/占用/磁盘失败、已提交状态保护、日志节流及联合退出预留。C# 恢复文案与回执契约在 `tests/winui_host/Program.cs`。实际 ODB 合并内容证据沿用 F013 的两组既有模型，不因状态存储变更重新求解。

2026-11-19的`packaging/verify_real_merge_backend_crash.py`已补验真实GJB副本和实际Abaqus校验进程仍存活时的后台强制退出：保守恢复、同请求不重放、现场保留、旧目标和来源摘要不变通过；原校验进程短暂停住以固定故障时序，恢复后退出120，未当作成功。准确范围与回执见[安全合并](../../03-features/ODB_MERGE.md)。
